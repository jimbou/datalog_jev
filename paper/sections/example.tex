We illustrate the problem and our approach with two verdicts from \texttt{org.jsl.wfwt}, a walkie-talkie app from F-Droid (Figure~\ref{fig:example}).
Both verdicts are about logging calls.
In method \texttt{handleStationName} of class \texttt{ChannelSession}, the app decodes a station name from a message buffer into a \texttt{CharBuffer}, converts it to a string and then calls \texttt{Log.w}.
In method \texttt{resolveNextLocked} of class \texttt{Channel}, it compares a service name with \texttt{String.equals} and then calls \texttt{Log.i}.

Our analysis does not model library code, so it finds no path from a source to either sink and reports both as clean.
With every library flow switched on, a source reaches both sinks, so both verdicts depend on library behavior.
For each verdict, the receipt is the single library flow that the verdict assumes absent.
For verdict A, it is the flow from a \texttt{CharBuffer} to the string that \texttt{toString()} returns: sensitive data can reach the log call only through this flow.
That flow is real, as FlowDroid's hand-written model of \texttt{CharBuffer} states, so verdict A misses a leak.
For verdict B, it is a flow from the argument of \texttt{String.equals} into the string itself: sensitive data can reach the log call only if comparing two strings copied one into the other.
Comparing two strings copies nothing, so verdict B is correct.

The existing answers cannot tell the two verdicts apart.
A sound analysis reports both as leaks, so the user must inspect B, a false alarm, and every similar sink in the app.
In our corpus, such alarms are 28\% of the sinks that never leak.
Listing the assumptions gives one fact for each verdict.
A count of assumptions treats them alike, and a rule that clears all one-fact receipts would clear A as well.
Asking a language model whether each flow exists, and taking the answer as fact, gives the right answer for these two facts.
It is still not a basis for clearing verdicts, because nothing controls how often such answers are wrong: across our corpus they leave wrong clearances in up to 8\% of the apps, at a rate the user can neither choose nor measure in advance.

Our approach prices each fact.
The pricer gives 0.95 to the \texttt{CharBuffer} flow and 0.03 to the \texttt{String.equals} flow, so the receipt of A costs 0.95 and the receipt of B costs 0.03.
A threshold of 0.3, certified on other apps so that at most 5\% of programs receive a wrong clearance, clears B and keeps A as a possible leak.
The user sees why: B is cleared because comparing strings does not copy them, and A is reported because converting a buffer to a string does.
If the price of a fact were wrong, the certified threshold would still bound how often such mistakes reach a user, and the receipt would show which fact to check.
